# **通用项目规范文档（Spec Docs）生成指南**

## **前言：如何使用此模板**

本指南提供了一个用于生成三阶段项目规范的通用模板。它的设计旨在让您严格遵循其结构和原则。所有方括号 `[...]` 内的内容都是占位符，必须用项目的具体细节替换。所有以 `例如，` 开头的内容纯粹是为了阐释格式，不应直接复制。

## **指导原则：“活文档”理念**

* **强力开局**：这些文档旨在大量开发工作开始前，最大化地明确目标、对齐共识。
* **拥抱变化**：计划总会变。将这些文档视为基线，微小的变更应在任务跟踪工具中进行。只有当核心范围或架构发生重大变化时，才需要回溯更新这些文档。

# **`scope.md` — 阶段一：意图与价值 (视角：项目经理)**

**目标与原则**: 本文档是项目意图的“契约”，旨在定义项目的“为什么”和“做什么”。**所有内容都必须围绕用户和业务价值展开**，为项目划定清晰的边界和可衡量的成功标准。**严禁在此处包含任何技术实现细节**，以确保需求是最纯粹的、面向结果的。

1. **项目概述**
    * *此部分旨在用最简洁的语言概括项目的核心。读者应在30秒内理解项目的目的和价值。*
    * **问题陈述**: `[用一句清晰的话描述要解决的核心问题，例如，“我们的客户缺少一种方法，能根据他们的自由文本搜索查询找到相关的产品。”]`
    * **目标用户/业务领域**: `[明确主要受益者，例如，“电商网站的购物者”或“内部市场营销部门。”]`

2. **用户故事与验收标准**
    * *此部分是范围的核心。每个用户故事都必须是可独立测试和交付的最小价值单元。验收信号必须是具体的、可量化的，它们是后续测试和验收的唯一标准。*

    | ID | 优先级 | 用户故事 | 验收信号 (可量化) |
    | :--- | :--- | :--- |:--- |
    | `US1` | P0 | 作为一名`[用户角色]`，我希望`[执行某个动作]`，以便`[达成某个目标]`。 | `例如，1. [一个性能指标，如 'P95 搜索延迟低于 300ms']。 2. [一个业务指标，如 '搜索结果的点击率提升 5%']。` |

3. **关键非功能性需求 (NFRs)**
    * *明确那些“隐形”但至关重要的质量属性。这些需求与具体功能无关，但决定了产品的生死，必须从第一天就得到重视。*
    * **性能**: `例如，系统必须在高峰期支持每秒 200 次请求 (RPS)。`
    * **安全性**: `例如，所有可识别用户身份的数据在静态存储时必须使用 AES-256 加密。`
    * **可靠性**: `例如，服务的正常运行时间必须保持在 99.9%。`

4. **约束与边界**
    * *清晰地划定“战场”。约束是必须遵守的硬性规定，而“不做范围”则通过主动放弃某些内容来保护核心价值的交付。*
    * **约束 (必须满足)**: `例如，必须使用公司现有的身份提供商进行认证。`
    * **不做范围 (不会做)**: `例如，本项目将不包括一个面向用户的管理后台。`

5. **假设与待澄清项**
    * *暴露项目中的“未知”。假设是项目成立的基础，如果被证伪，项目可能有风险。待澄清项是需要与干系人沟通以消除模糊地带的具体问题。*
    * **假设**: `A1`: `例如，我们假设上游数据源有可靠的每日更新计划。`
    * **待澄清项**: `NC1`: `例如，用户活动日志的数据保留策略是什么？ (默认提议: 90 天)。`

6. **阶段门禁：准备好进入架构设计了吗？**
    * `[ ]` 所有 P0 级用户故事都已定义，并有可量化的验收信号。
    * `[ ]` 关键的非功能性需求已被明确提出。
    * `[ ]` 待澄清项少于 3 个，并都给出了默认提议。

# **`architecture.md` — 阶段二：技术策略 (视角：架构师)**

**目标与原则**: 本文档是连接“需求”与“实现”的桥梁。它必须**在充分理解`scope.md`的基础上，评估并确定一个可行的技术方案**。重点是进行多维度权衡（成本、风险、维护性等），并清晰地记录决策过程。**严禁在此处引入新的需求或具体的任务列表**。

1. **前言：范围确认**
    * *首先复述并确认你理解的目标，确保架构设计与项目范围完全对齐。*
    * **目标**: “本架构旨在实现 `scope.md` 中定义的用户故事 `US1`, `US2`, ... 并满足其中陈述的所有非功能性需求。”

2. **方案评估**
    * *这是架构设计的核心。必须对至少两种可行方案（包括“维持现状”）进行客观、多维度的比较，让决策过程透明化。*

    | 方案 | 简介 | 优点 | 缺点 | 结论 |
    | :--- | :--- | :--- |:--- |:--- |
    | **A** | `例如，一个无服务器、事件驱动的方案。` | `例如，能自动扩展，空闲成本低。` | `例如，可能存在冷启动问题，调试复杂。` | **推荐** |

3. **推荐架构 (`DEC-A`)**
    * *详细描述被选定的方案。应在组件和数据流的层面上进行阐述，明确服务边界、集成点和数据契约，但避免陷入代码级别的实现细节。*
    * **高层图/数据流**: `[用一段文本描述主要组件和数据流，例如，“用户请求 -> API网关 -> Lambda函数 -> DynamoDB。”]`
    * **技术栈**:
        * **主要语言**: `例如，Go, Python`
        * **主要数据存储**: `例如，PostgreSQL`
    * **设计理念与开放性问题**: `[用于记录无法放入结构化表格的思考，例如，“我们的设计优先考虑了可扩展性，而非初始开发速度。一个开放性问题是，这种方法的长期成本影响如何。”]`

4. **风险与缓解措施**
    * *主动识别技术方案中潜在的风险，并给出具体的缓解计划。这会将未知风险转化为可管理的任务。*
    * **技术风险**: `R1`: `例如，所选的数据库在高写入负载下可能无法满足低延迟的NFR。` **缓解**: `例如，在计划的阶段0中进行概念验证（PoC）基准测试。`

5. **阶段门禁：准备好进入开发计划了吗？**
    * `[ ]` 推荐的架构已获得技术领导的批准。
    * `[ ]` 方案清晰地阐述了将如何满足所有关键的NFRs。
    * `[ ]` 主要风险已被识别，并分配了缓解策略。

# **`plan.md` — 阶段三：执行路线图 (视角：开发者)**

**目标与原则**: 本文档是将已批准的架构转化为**一份具体的、有序的可执行任务清单**。它必须具备极强的可操作性。**所有任务都必须追溯到`architecture.md`的决策或`scope.md`的需求**。**严禁在此处引入任何新的需求或架构决策**。

1. **前言：计划概述**
    * *明确本计划的依据和执行规则。*
    * **架构引用**: “本计划旨在执行 `architecture.md` 中定义的‘推荐架构’ (`DEC-A`)。”
    * **执行逻辑**: “任务按推荐的执行顺序列出。一个任务默认依赖其前一个任务的完成。在一个任务块中，被标记为 `[Parallel]` 的多个连续任务，表示它们可以并行执行。”

2. **分阶段任务清单**
    * *将整个项目分解为多个逻辑阶段，每个阶段都有一个明确的检查点（Checkpoint），用于验证阶段性成果。每个任务都应该是一个有明确交付物的小工作单元。*

    **阶段 0: 准备与研究**
    * *检查点: 所有必要的工具、环境和知识准备就绪。*
    * [ ] **T0.1 (P0)**: 建立代码仓库和基础的CI/CD流水线。 **[交付物：`例如，一个 README.md 文件和一个基础的、能通过的构建脚本。`**]

    **阶段 1: 核心基础**
    * *检查点: 应用的骨架已能运行，并能连接到其核心依赖。*
    * [ ] **T1.1 (P0)**: 使用`[例如，Terraform]`部署核心基础设施。

3. **最终上线准备清单**
    * *在所有开发工作完成后，用于确保万事俱备的最终检查列表。*
    * `[ ]` 所有 P0 级任务已完成。
    * `[ ]` `scope.md` 中所有故事的验收信号都已在类生产环境中通过验证。
    * `[ ]` 所有NFRs（性能、安全）已通过测试验证。
    * `[ ]` 监控仪表盘和告警已配置完成。
